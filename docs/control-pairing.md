# Operator-provisioned phone control

This authenticates possession of a separately paired control key. It does not identify a physical human, bind a hardware authenticator or log into OCI. Paired grants control the fixed [synthetic fixture](private-fixture.md). The registered experimental OCI CLI worker requires an additional private acceptance receipt before target selection or startup; see [the gated OCI flow](oci-host-flow.md).

## Trust boundary

An owner explicitly installs the first root using the offline utility. Runtime HTTP, RPC, native tools and the registered plugin CLI cannot create, replace, export or move that root. Missing/unsafe roots fail closed. BB secret input is confidential delivery, not proof of who submitted it. The offline importer also requires the public pairing fingerprint independently approved by the owner, so a substituted staging key does not silently become the expected root.

The control key is 32 random bytes generated by Web Crypto on the phone. The host stores only SHA-256 of those bytes. The public fingerprint is SHA-256 of `UTF8("bb-remote-login pairing root v1\0") || keyBytes`; its domain differs from the stored verifier. Keys and control tokens are never URL parameters, plugin metadata, realtime payloads, normal tool results or logs.

The host operator and BB global administrator are trusted. This API boundary does not isolate an arbitrary same-UID process, global filesystem administration, plugin replacement, or hostile same-origin plugin code from the host/user. Those actors can replace the verifier or the program itself.

## Owner setup

1. In iPhone BB App, open the plugin's **手机配对** page, select the intended host and check the connection/status. The initial probe sends no credential and requires the actual private route's precise 401/no-store response.
2. Generate a control key locally and save it in the phone's password manager before leaving the page. Send only its 64-hex public fingerprint to the trusted operator. Never send the 43-character control key in chat.
3. The operator obtains the fixed plugin data directory with `bb remote-login provisioning-info <host-id> --json`. This command cannot initialize anything.
4. On that host, prepare a fresh private staging directory outside both Git and the plugin data directory. Use `bb secret request REMOTE_LOGIN_CONTROL_KEY --write-env <exact-staging-file>` for confidential delivery. Do not inspect the completed file with agent-visible tools.
5. The trusted owner invokes the deterministic importer on that same host, passing only file paths and the approved public fingerprint:

```sh
node --experimental-strip-types scripts/provision-control.ts \
  --data-dir <fixed-plugin-data-directory> \
  --secret-file <fresh-private-staging-file> \
  --expected-fingerprint <owner-approved-public-fingerprint>
```

The utility creates `control-root.json` exclusively, never overwrites a root, and consumes only the original safe staging inode on success or failure. It rejects staging within the plugin's persistent data directory (including aliases). Use only this attempt's new staging file, never an existing credential file. Unsupported metadata or replacement inodes are left untouched and reported as a generic failure.

6. Refresh the phone status, paste the saved key into **验证控制密钥**, and verify the protected control route. The key is cleared from the input; the returned opaque grant remains only in component memory. No grant is printed. Expiry returns the page to an unprivileged state.

7. Before using the experimental OCI CLI controller, complete a protected native synthetic request and hand it back. Only successful host verification followed by confirmed closure can create the private OCI control acceptance receipt. Refresh OCI startup conditions afterward; a successful ordinary control check is insufficient.

No actual owner key has been provisioned by the automated fixture tests. Real iPhone delivery and operator setup still require live verification.

## Runtime protocol

The plugin's HTTP routes retain BB's local/app auth and add independent control-key/token checks. Transport must be HTTPS or local loopback; the phone uses only its active native server, or the current page origin in ordinary web mode. Unknown mobile server state and remote plaintext HTTP are not credential fallbacks.

| POST path below `/api/v1/plugins/remote-login/http` | Independent proof | Result |
|---|---|---|
| `/control/session` | Paired control key | New short-lived opaque grant |
| `/control/check` | Bearer grant | Non-secret authorization check |
| `/control/renew` | Current bearer grant | New token; old token invalid |
| `/control/release` | Current bearer grant | Revoke that token |

All responses are no-store. Body size is capped at 4096 bytes; fixed error responses do not echo submitted material or backend exceptions. Grants are bound to the worker/host, threadId, attemptId, browserContextId, generation, root version and expiry. They last five minutes; renewal cannot exceed fifteen minutes from initial proof. A worker replacement or root change invalidates old grants. Host lifecycle and browser lease generation checks are enforced separately by the synthetic and OCI workers.

An accepted `/control/check` also persists one non-secret historical receipt per host in plugin KV. Public `controlStatus.lastCheck` contains only `checkedAt` (server wall-clock milliseconds), `hostId` and the exact scope. Acknowledgment waits for persistence; per-host writes are serialized, failures do not erase an earlier receipt, and malformed or cross-host stored records are hidden. Keys, capabilities, URLs and browser data are excluded. Only an accepted check creates a receipt; session creation, renewal and release do not.

The receipt survives plugin/worker replacement as historical evidence. It does **not** assert that a grant is still usable, identify an iPhone or human, verify OCI authentication, or authorize task resumption. Live validation must match the expected scope and a check time after that round started, and independently verify the phone action. A released/expired grant or replaced root does not erase history. Neither an old receipt nor an untrusted client-supplied timestamp is evidence of a new round.

Renew and release consume the current token. If a concurrent renewal already consumed it, release refuses instead of falsely reporting that the newly issued token was revoked. A successful release also stops any matching current-worker fixture/OCI scope. Before OCI startup, the job gateway uses revocation to stop even an unconfigured control session. Neither revocation nor absence from a replacement worker proves that unknown older resources were removed.

Guessing is restricted by a persistent rolling five-attempt/sixty-second budget reserved before checking the key. Lock/budget corruption fails closed. A hard process crash can leave a lock; operator recovery requires first confirming the worker stopped, preserving the budget/root and removing only the owned stale lock. Automatic stale-lock recovery and clearer failure UX remain part of the reliability work, not a claimed capability here.

## Private OCI control acceptance

The ordinary `/control/check` KV receipt above is historical status only. It cannot unlock OCI. The separate host-only `PairedControlGate` producer verifies an owned synthetic fixture, confirms that exact browser's closure, rechecks control/root generation, then atomically persists a safe private receipt. Public HTTP/RPC/native inputs cannot supply a gate boolean, receipt or timestamp.

The receipt binds the chosen host or remote control mode; one mode cannot authorize the other. See [host login](host-login.md). That private receipt lasts exactly 24 hours and must match the current root generation and `private-fixture/Chrome-157.0.8103.51/v1` pin. Unsafe or malformed storage, replacement during a read, expiry or a different generation/pin fails closed. OCI status can report whether this control-path gate is accepted; configuration, startup, ongoing operations and live resume proof recheck it. The receipt proves paired key possession and a verified control path, not physical iPhone identity or OCI authentication. No real owner fingerprint/key or actual phone acceptance has been used in this work.

## Evidence

- Public SDK harness exercises the real authority through host RPC and HTTP, including cross-host/context/thread/generation rejection, renewal/revocation and worker replacement.
- Real child-process tests exercise the offline importer, staging encodings, ownership/permissions/symlinks, malformed input and inode races.
- Browser crypto has an independently computed fingerprint fixture. Public frontend harness tests web/null and native server selection, no-secret preflight, key clearing, non-rendered grants, local key generation and expiry.
- Production iPhone UI, real owner provisioning, private browser input and OCI authorization are not proven by those fixtures.
