# Durable login coordination

The coordinator stores non-secret attempt state, not authentication material. Native tools can request, query and cancel synthetic or separately gated experimental OCI CLI and Console attempts. OCI CLI queues only after a matched source inventory and uses separate private startup/verification gates. `oci_web` queues on the supported macOS arm64 runtime and uses separate private target, paired-control, pinned browser/source and identity gates. Fixture success is not a live OCI login or production-delivery claim.

## Trusted target

Native tools accept a mode or attempt identifier only. They use the injected project/thread context, fetch that thread and its environment through the public SDK, require a ready active environment on an active host, and use that environment's `hostId`. There is no fallback to the server's computer or a model-selected host. Request creation rechecks the binding after observing the selected host's control root and fixed method/runtime eligibility report. Status and cancellation isolate jobs to the injected thread and project, then re-resolve the environment and read the latest revision.

The durable binding includes project, thread, environment, host, attempt, browser context, generation and principal. The principal is the host-observed control-root identifier; it does not prove a physical human or device. Root observation can bind a waiting request but cannot authorize browser input. That still requires independent private control proof. OCI additionally requires the private verified-and-closed synthetic control receipt and a target selected through protected HTTP before startup; expected OCIDs never enter the coordinator record.

## Persistence and concurrency

The public SDK supplies the plugin's SQLite handle. Append-only SDK migrations create strict JSON attempt records, indexed immutable identity/deadline fields, a unique active request per project/thread/mode, an owner epoch and a cleanup outbox. Each transition uses a synchronous immediate transaction and compare-and-swap against revision and owner epoch. No SDK, host or network await occurs inside a database transaction.

SQL failures roll back the entire transition, including cleanup insertion. A domain deadline refusal can commit an explicit expiry before the refusal is returned; a failed cleanup insertion cannot leave a cancelled attempt without its command. Corrupt or extra-field records fail closed with fixed errors. IDs are generated by the coordinator, and secrets, browser content, input, provider URLs, filesystem paths and backend exceptions are not stored.

Construction is inert. `activate()` must run from a committed service or handler, never a candidate plugin factory. A rejected candidate therefore cannot take ownership from a still-running plugin. Activation fences the prior owner. It preserves safe waiting records, expires overdue records, and terminates unfinished resource phases as `worker_lost`; it never promotes them to verified. Claimed delivery retains its identifier and remains uncertain. Old asynchronous callbacks cannot write through the new owner's epoch.

## Expiry and owned cleanup

The committed background service sweeps due attempts and processes cleanup commands by recorded host/scope. Commands survive reload and failure. A sorted cursor prevents a failed command from starving later commands. Host calls have an eight-second cancellation race, and a timeout, cancellation or stale-owner reply cannot acknowledge cleanup. Retrying a stop operation is allowed; input is never retried by this service.

The host stops only a matching plugin-owned lease. An active or known closed scope can confirm cleanup after it completes. An unknown scope or replacement worker returns `cleanup_uncertain`; absence from a new worker's memory is not evidence that an older process or profile was removed. Such commands stay pending. No unknown profile is automatically deleted. The OCI host can reconcile an exact durable resource journal after its old owner and non-browser writers are absent and browser cleanup is already durable. Unknown/replaced files, interrupted ownership gaps and non-closed browser writers remain pending. This restores cleanup evidence only, never session or task authority; see [resource recovery](owned-resource-recovery.md).

## Verification and original-task recovery

The protocol keeps authentication phase and continuation bookkeeping separate. Verification must come from a restricted matching provider, with the expected host, target resource, identity and task scope checked privately. Synthetic evidence never verifies OCI. An ordinary form submission or client flag cannot create verification; the public RPC is read-only and there is no public event setter.

`prepareResume()` is internal. It can run only after matching verification and before the deadline. In one transaction it claims a generated delivery identifier and records `uncertain` before a caller could attempt delivery. Repetition is refused. Cancellation or reload after a possible delivery does not pretend the result was unsent.

SDK 0.6.132 provides neither a native tool-call identifier for durable reattachment nor a delivery acknowledgement for `requestInput`'s eventual system message. `threads.send` also has no idempotency key. The implementation does not blind-resend or label a claim `delivered`. The schema's delivery acknowledgement is reserved for a future trusted observation; no current UI, RPC or native tool can produce it. Synthetic, CLI and Console verification paths are connected to their original native result in source. OCI completion also requires an internal receipt-to-live-lease proof, matching artifact generation seal and unexpired private authority after the final await. The opaque `accountRef` is a live-worker result reference. A fixed read-task consumer requires the same injected context, verified receipt, current host binding, unexpired lease and sealed files; it cannot export credentials or run arbitrary commands. Before any OCI claim or task result returns, the final asynchronous check is a live private host proof of that same reference and lease; task reads then synchronously recheck the durable attempt for cancellation/revision changes. Public root ID alone cannot replace this proof, including when a root file is replaced without changing that ID. SDK binding observation and host authority are separate asynchronous domains; these checks do not constitute a cross-system atomic transaction. Production delivery still needs a live experiment and reconciliation policy.

## Current user surfaces and limits

Ordinary login tools are available in each injected thread. `probeThreadId` opts only that thread into the diagnostic wait fixture; it grants no browser or account authority:

- `remote_login_request`: observe the actual target and queue a synthetic or source-compatible OCI CLI request; optional `wait:true` opens the protected controller interaction and rechecks independent verification before returning. An OCI request alone grants no browser or account authority. Console has its own independently verified browser reference.
- `remote_login_console_read`: after original-call handback, verify the retained Console identity or read the current title and up to twenty headings in that same browser context.
- `remote_login_status`: return a bounded non-secret state for the current thread's attempt.
- `remote_login_cancel`: record cancellation without claiming that pending cleanup completed.
- `remote_login_oci_read`: after original-call handback, list up to 25 accessible compartments or Sydney instances through the matching live session; explicit truncation and opaque compartment references keep the bounded scope clear.

The **登录会话** panel reads the SDK-selected thread's history. It offers manual refresh, drops late results on a thread switch or local timeout, and opens the protected controller for a live synthetic or OCI attempt. The controller still requires independent key possession. The frontend SDK cannot physically cancel the underlying RPC; the panel only refuses to consume its stale result.

See [protected takeover](login-flow.md) and [the registered OCI host flow](oci-host-flow.md). The CLI host adapter and official/independent verifier chain are connected. Existing-session reuse, arbitrary task operations, uncertain browser-orphan recovery, production result delivery and real iPhone/OCI acceptance remain incomplete. No real owner fingerprint/key or OCI authentication was used. Installed/source parity is unverified; the current source has not been live-accepted; the historical explicitly loaded diagnostic revision was `36b57ef`.
