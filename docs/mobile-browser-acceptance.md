## Mandatory displayed-frame contract: current increment

Private synthetic, CLI and Console frames now carry an opaque private UUIDv4 `frameRef`; each input must name the reference from its displayed image as well as its separately generated `inputId`. The browser issues the reference after capture and existing postchecks, and known capture/page/frame-tree/viewport or authority changes invalidate it. The required private callback spends `inputId` before checking stale-frame state, so a lost-ACK retransmission cannot be mistaken for a new harmless refusal. Existing capability/root/owner/scope/generation/deadline and post-operation checks remain in force. See [the full input contract](input-replay.md).

A trusted input `StaleFrameError` means that input was refused before its effect. The viewer clears the image, retains unsent text when applicable and permits a fresh bounded read; another input still requires user action. A separate `FrameChangedError` means only that a read could not publish its image. In particular, when input was acknowledged and the following read changed, the controller must not call the input unsent or retry it. Existing polling or the refresh button can obtain a new observation without replaying input, restarting login, reauthenticating or extending authority.

This detects superseded observations and known changes; it does not freeze arbitrary DOM/layout/animation changes or provide atomic screenshot-to-click pixel identity. The host viewport remains fixed at 800×600/DPR1; phone rotation changes the displayed CSS mapping, not permission to resize the host. Verification-only Console rejoin still denies frame/input/start.

The dropped-ACK case still sees two HTTP requests with the same inputId/frameRef, one delegated keyboard effect and generic input uncertainty; the controlled provider navigation case also passed. These are actual Chrome, source frontend/current CSS, loopback service and public SDK testing observations. ## Callback document barrier

A controlled real-browser red dispatched capture after the actual callback root response but before document commit. Chrome returned a real `ProtocolError` with exact `Not attached to an active page` while the old provider URL and original open/connected target/context remained valid; the private frame returned 403. This is distinct from the earlier exact `Unable to capture screenshot` recovery and from the still separately assessed normal-flow failure.

The existing request handler now pre-arms one DOM-content-loaded wait **before** continuing an allowed GET main-frame document request to HTTP localhost/127.0.0.1:8181 at `/` or `/token`. A private marker holds only a void promise and local cancellation controller. Frame capture awaits the captured marker once, rechecks ownership/all-frame policy, then requires that same marker and fixed callback URL before consumption and its first screenshot. Supersession/close abort the old wait; another main-frame document clears it. Token XHR, subframes, POST and provider documents cannot create a callback barrier. Rejection, cancellation, wrong final URL or replacement refuses instead of looping onto another wait.

The wait is bounded to one second inside the original operation deadline. Puppeteer **25.16.0** supplies `ignoreSameDocumentNavigation`, an explicitly pinned vendor option annotated `@internal` and stripped from its top-level generated declaration. The code uses a narrow extension of the public `Page.waitForNavigation` parameter type, with no `any`, deep import or BB-private API. Typing alone does not prove runtime semantics.

[The controlled test](../tests/oci-provider-navigation.test.ts) therefore probes a steady provider document **before callback input**: a real hash/history change fulfills the default wait; a second real change leaves the flagged wait pending, then that probe is aborted and drained. The production wait is observed separately and must be pre-armed exactly once, fulfill at callback document readiness and precede capture. The earlier attempt to evaluate JavaScript while callback navigation was held produced no hash event/capture; its failed fixture log is preserved and is not a product failure or a passing probe.

The corrected controlled run passed 1/1: root response→commit→one capture, HTTP 200, zero capture failures, one input/root/token continuation each, real bootstrap→diagnostic→SDK verification→bounded task/original native `resume:"uncertain"`, and confirmed browser/profile closure. [Provider unit tests](../tests/oci-provider-browser.test.ts) passed 44/44, covering barrier order, cancellation, same-turn supersession, wrong ownership/URL and excluded requests. This does not prove a universal navigation fix: navigation beginning after a frame snapshots no marker and the normal unknown fault remain separate scope.

The existing exact `Unable to capture screenshot` path still permits only one identical read retry after its bounded rendering opportunity and fresh checks. No inactive-page error retry, input retry, fallback PNG, new browser permission or deadline extension was added. Diagnostic classification uses nonempty `originalMessage` or the stripped message when empty, exporting fixed flags only. Host `aborted`/child `cancelled` results can be cleanup consequences and do not identify the original error.
